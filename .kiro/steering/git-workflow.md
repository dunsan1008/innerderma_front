# Git 커밋·푸쉬 규칙

## 작업 완료 시 절차 (항상 이 순서로)

1. **작업을 마치면 먼저 커밋한다.** 사용자가 따로 요청하지 않아도 커밋까지는 진행한다.
2. 커밋 후 **푸쉬 여부를 사용자에게 묻는다.** 임의로 푸쉬하지 않는다.
3. 사용자가 푸쉬하라고 답하면 푸쉬한다.

## 대상 브랜치

- 이 저장소는 **`main` 브랜치에 직접 커밋·푸쉬**한다. (사용자 지시)
- 원격: `origin` → `https://github.com/dunsan1008/innerderma_front.git`
- 별도 브랜치를 만들지 않는다. 사용자가 브랜치를 지정하면 그때만 따른다.

## 커밋 작성 규칙

- 커밋은 **관심사 단위로 쪼갠다.** 성격이 다른 변경(예: 마켓 화면 개선 / 검증 도구 추가 / 캘린더 수정)은 각각 별도 커밋으로.
- 메시지는 한국어로 쓴다. 제목은 한 줄로 간결하게, 본문에 변경 이유와 항목을 적는다.
- `git add .` / `git add -A` 대신 **파일을 이름으로 지정해 스테이징**한다.
- 커밋 전에 `git status` 로 내가 수정하지 않은 파일이 섞여 있는지 확인한다.
  이전 세션에서 남은 미커밋 변경이 있을 수 있으므로, 내용을 확인하고 **별도 커밋으로 분리**한다.
  남의 작업을 내 변경으로 뭉쳐 커밋하지 않는다.

## 커밋 전 확인

- 빌드(`npm run build`)가 통과하는지 확인한다.
- 검증 스크립트가 있으면 돌린다 (`node scripts/verify.mjs`, `node scripts/verify-i18n.mjs`).
- 검증용으로 만든 임시 스크립트·산출물은 커밋에 포함하지 않는다.

## 하지 않는 것

- `--amend`, `--force`, `reset --hard` 등 이력을 되돌리는 명령은 사용자가 명시적으로 요청할 때만.
- `--no-verify` 로 훅을 건너뛰지 않는다.
- `.env` 등 비밀값이 들어 있을 수 있는 파일은 스테이징 전에 사용자에게 알린다.
